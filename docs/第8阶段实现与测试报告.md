# 4 计划周期设计

| 周期类型 | 计算规则 | 实际编码 |
|---|---|---|
| 周 | 基准日期 `plusWeeks(N)` | `WEEK` |
| 月 | 基准日期 `plusMonths(N)` | `MONTH` |
| 季度 | 基准日期 `plusMonths(3 × N)` | `QUARTER` |

日期计算集中在 `MaintenanceScheduleService`。过期补跑只生成一张当前待办，再循环推进到首个晚于扫描日的日期；Java `LocalDate` 自然处理月末和跨年边界。

# 5 Spring Scheduling

扫描周期：默认每小时整点，配置项 `app.maintenance.scan-cron=${MAINTENANCE_SCAN_CRON:0 0 * * * *}`。

扫描条件：计划为 `ENABLED` 且 `next_execute_date <= 当天`。

生成逻辑：Scheduler 只调用扫描服务；生成器在事务内检查计划、设备、检查项，写统一 PM 工单和 CREATE 流转日志，然后推进日期。

错误处理：单计划异常记录日志和失败计数，不阻断后续计划；测试环境可直接调用扫描服务，不等待定时器。

# 6 幂等设计

对计划执行 `SELECT ... FOR UPDATE`，串行化同一计划的并发生成；锁内再次验证启用状态和到期日期。日期推进采用“计划 ID + 原日期”条件更新，工单、日志、日期在同一事务内提交或回滚。重复扫描看到的新日期已在未来，因此不会重复生成当前周期工单。

# 7 保养工单

自动生成的工单写入既有 `mnt_work_order`，类型为 `MAINTENANCE`，初始状态为 `PENDING_ASSIGN`，`repair_request_id` 为空，`pm_plan_id` 为来源计划。编号沿用业务编号服务并使用 PM 前缀。

# 8 工单类型关系

维修与保养共用：工单列表/详情、编号、设备、班组、工程师、派单、接单、开始、挂起/恢复、提交验收、退回/通过、取消、时间字段、权限和流转日志。

维修差异：来源于报修，要求维修记录，联动 `FAULT → REPAIRING → RUNNING`，可领用维修备件。

保养差异：来源于计划，展示检查项与执行结果，不要求故障或维修记录，不触发故障状态，不启用备件领用。

# 9 保养检查项目

计划可维护项目名称、检查标准、顺序和必检标记。至少配置一项。计划一旦生成工单，检查项目禁止整体覆盖，避免后续修改污染历史工单的解释口径。

# 10 工程师执行流程

主管在工单中心派单；被指派工程师接单并开始保养，在 PM 详情逐项填写 `NORMAL/ABNORMAL`、可选测量值和备注并保存。提交验收前服务端检查全部必检项；主管验收通过后工单完成，验收退回则继续处理。非指派工程师、错误状态或非 PM 工单均不能写执行结果。

# 11 设备状态处理

PM 是预防任务，不代表设备故障。开始 PM 时不把运行设备改为 `REPAIRING`，完成时不强制写回 `RUNNING`，更不会写入 `FAULT`。维修工单原有 `FAULT → REPAIRING → RUNNING` 状态联动保持不变，并由全量回归覆盖。

# 12 设备保养履历

履历由 `mnt_work_order + pm_plan + pm_execution_item` 实时查询，展示工单、计划、状态、工程师、完成项、异常项、生成与完成时间。设备详情新增“保养计划/保养记录”页签，计划页提供单计划履历。

# 13 与库存模块联动

PM 未使用备件联动。Stage 7 后端规则仍为“仅处理中的维修工单可领用备件”，PM 页面不展示维修备件入口。原维修工单的领用、扣减、退库、流水与关单后限制已在 Stage 7 全量数据库回归中通过。
