# 4 候选工程师过滤

先过滤再评分：用户和角色必须启用、具有 `ENGINEER` 角色、所属班组未停用；调用人必须通过既有 `assertCanAssign` 权限与工单数据范围检查。管理员可看全部合法工程师；主管候选只来自其负责车间或授权班组。推荐仅允许 `REPAIR + PENDING_ASSIGN`。候选为空返回空列表，前端提示“当前没有符合条件的可派工程师”，不补管理员或无关角色。

# 5 智能派单评分公式

实际公式：`S = 0.40 × S_skill + 0.30 × S_load + 0.20 × S_team + 0.10 × S_area`，权重来自 `application.yml`，非负且总和必须等于 1，否则业务调用明确拒绝。

`S_skill = 匹配技能数 / 所需技能数`；`S_load = 1 / (1 + activeOrderCount)`；同班组、同车间分别取 1，否则取 0。各维度范围均为 `[0,1]`。设备类型未配置技能时不计算技能维度，并对剩余 0.60 权重重新归一化，避免 `0/0`、NaN 或无依据的技能分。

# 6 Top 3排序

顺序为总分降序、技能分降序、当前负载升序、班组分降序、工程师 ID 升序。合法候选不少于 3 时返回 3 人，不足时返回实际人数，为 0 时返回空列表。同一输入与数据库快照下排序确定。

# 7 推荐解释

真实响应字段包括 `engineerId/name`、班组、`totalScore`、四个子分、`currentActiveOrders`、`matchedSkills`、`requiredSkills` 和 `recommendationReasons`。理由由数据直接生成，例如“匹配 1/2 项技能”“当前 0 张在处工单”“与设备属于同一负责班组”“负责当前车间”。

# 8 主管确认派单

推荐接口为只读事务，不修改负责人、状态和流转日志。主管可点选 Top 1/2/3，也可在既有合法工程师下拉框选择其他人；确认后仍调用原 `POST /assign → WorkOrderService.assign()`，重新验证工单状态、工程师合法性、权限和数据范围，并写原有 ASSIGN 流转。

# 11 实验分析

在该固定样本中，加权方案提高了技能、班组和区域匹配以及既定公式下的综合分；最低负载方案的 CV 和极差更低，负载均衡明显更强。结果揭示能力/属地匹配与负载均衡的权衡，不证明当前权重对所有企业数据最优。样本较小且无排班、预计工时等变量，是后续标定的主要限制。

# 12 SLA规则

| 故障等级 | 响应 SLA | 解决 SLA | 实际编码 |
|---|---:|---:|---|
| 紧急 | 30 分钟 | 240 分钟 | `URGENT` |
| 重要 | 120 分钟 | 480 分钟 | `IMPORTANT` |
| 一般 | 240 分钟 | 1440 分钟 | `NORMAL` |

规则可启停、修改；时限必须为正且响应时限不能超过解决时限。数据库 `priority` 唯一，避免同等级冲突。

# 13 SLA时间语义

开始：维修工单 `created_at`。响应完成：工程师接单写入 `accepted_at`。解决完成：验收通过写入 `completed_at`。挂起处理：第一版连续计时，不暂停。取消处理：`CANCELLED` 不再产生新事件。`MAINTENANCE` 不绑定故障 SLA，也不进入扫描。

# 14 SLA数据模型

| 表 | 作用 | 主要关系 |
|---|---|---|
| `mnt_sla_rule` | 三类优先级的响应/解决规则 | `priority` 唯一 |
| `mnt_work_order` | 冻结建单时的规则和两个截止时间 | `sla_rule_id`、`sla_response_deadline`、`sla_resolve_deadline` |
| `mnt_sla_event` | 响应/解决超时与处理状态 | 关联工单、规则、升级用户、消息；工单+事件类型唯一 |
| `msg_notification` | 当前用户站内消息和已读状态 | `receiver_id`；通过 `business_type/id` 关联工单 |

# 15 SLA定时扫描

默认 Cron 为 `0 */5 * * * *`，即每 5 分钟。只扫描 `REPAIR`、非 `COMPLETED/CANCELLED`、已绑定规则且 deadline 已过的工单；响应扫描额外要求 `accepted_at IS NULL`。Scheduler 只调用 Service；单条异常记录日志并继续处理后续工单，测试直接调用 Service，不使用 `sleep`。

# 16 SLA超时幂等

数据库唯一键 `uk_sla_event_order_type(work_order_id,event_type)` 是最终幂等边界；服务使用 `INSERT IGNORE`，只有首次插入成功才创建消息并回写 `message_id`。同一工单的响应和解决事件各最多一条，重复扫描不会重复通知。

# 17 SLA升级

升级对象按真实组织数据确定：先取设备 `responsible_team_id → org_team.leader_id`，要求用户启用且具有启用的 `MAINTENANCE_SUPERVISOR` 角色；若无有效班组长，再取设备所属 `station → line → workshop.manager_id`，同样校验主管角色与状态。全程不硬编码用户 ID。两者均不存在时保留未处理 SLA 事件并写明原因，不发给随机用户。

# 18 站内消息

首次 SLA 事件成功插入后生成一条 `message_type=SLA` 消息。列表、未读数、单条已读和全部已读均强制使用当前登录用户 ID；越权标记返回不存在。SLA 消息使用 `business_type=WORK_ORDER` 和工单 ID 跳转。事件唯一键和“先事件后消息”共同保证不重复。
